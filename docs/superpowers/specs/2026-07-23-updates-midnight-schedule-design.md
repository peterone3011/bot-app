# 日常贴凌晨限次发布设计

## 目标

将 `cogs/updates.py` 从全天每 5 分钟轮询 Lark Bitable，改为仅在北京时间凌晨读取和发布，减少 Lark API 消耗，并避免 Bot 白天重启时突然补发历史日常贴。

## 时间规则

- 每天北京时间 `00:01` 首次检查。
- 仅在本次检查失败时，于 `00:06` 和 `00:16` 重试。
- 首次检查读取成功且无目标记录，视为当日成功，不再读取。
- 目标记录全部发布成功，视为当日成功，不再读取。
- Bot 仅在北京时间 `00:00–00:30` 启动时允许补查。
- Bot 在 `00:00–00:01` 启动时等待 `00:01`，不提前读取。
- Bot 在 `00:01–00:30` 启动时允许立即补查一次，并继续等待尚未到达的固定重试时间。
- Bot 在其他时间启动时只启动服务，不读取 Lark，也不发布日常贴。
- 使用进程内的当日状态和异步锁，防止固定时间任务与启动补查在同一进程中重复执行。
- 不持久化每日尝试次数；凌晨反复重启可能产生额外读取，该边界可接受。

## 日期筛选

每天的任务只处理：

1. 状态为 `待发布`；
2. 记录日期严格等于北京时间的昨天。

例如：

- `2026/07/23` 的记录仅在 `2026/07/24 00:01–00:30` 的任务中处理。
- 当天新增且日期为当天的内容，不会当天发布。
- 若该记录在目标凌晨未发布成功，`2026/07/25` 及以后不会自动补发。

现有 `record_date < today` 判断必须收紧为 `record_date == today - 1 day`，防止历史待发布内容在后续日期突然发出。

## 单次检查结果

单次检查返回明确结果，供调度器决定是否继续重试：

- `success`：Lark 读取成功，且没有目标记录；或所有目标记录均发布并完成状态处理。
- `retry`：Lark 读取失败、目标频道不可用、图片下载失败、状态写入失败、Discord 发送失败，或存在任何未完成的目标记录。

当一批记录中只有部分失败时：

- 已成功记录保持 `已发布`，后续检查不会重复发送。
- 仍为 `待发布` 的昨天记录在下一个固定时间重试。
- 单条记录失败不阻止同批其他记录继续处理。

现有的防重复顺序保持不变：

1. 发布前写入 `发布中`；
2. 发送 Discord；
3. 成功后写入 `已发布`；
4. Discord 发送失败时尝试恢复为 `待发布`。

## 最终失败

- `00:16` 的检查仍失败，或 `00:16–00:30` 启动补查仍失败时，当日自动处理结束。
- Railway 日志记录日期、失败阶段、record ID 和异常信息。
- 通过现有 `LARK_NOTIFY_CHAT_ID` 发送人工处理告警。
- 失败记录不在白天重试，也不在次日自动补发。
- 不新增 Lark 状态值；记录保持现有状态，由人工检查和处理。

## API 使用量

- 正常情况：每天读取 Bitable 一次，每月约 30 次。
- 发生可重试失败：每天最多三个固定时间读取，每月最坏约 90 次。
- 发布记录时仍需要 Token 获取、图片下载和状态回写等必要 API 调用；本设计限制的是全天列表轮询读取。
- 因不持久化调度状态，凌晨窗口内反复重启可能超过三次读取。

## 测试范围

自动化测试至少覆盖：

- 昨天的待发布记录符合条件。
- 今天、前天、更早及未来记录均不符合条件。
- 已发布、发布中、无日期和非法日期记录均不符合条件。
- `00:01、00:06、00:16` 为固定检查时间。
- 成功或无目标记录后跳过当天剩余检查。
- 失败时允许下一固定时间重试。
- 白天启动不读取、不发布。
- `00:00–00:01` 启动等待首次检查。
- `00:01–00:30` 启动允许一次补查。
- `00:30` 后启动不补查。
- 启动补查与固定任务不会并发读取。
- 最终失败会记录错误并发送 Lark 告警。

## 不在范围内

- 严格跨进程、跨部署限制每日读取次数。
- Railway Cron 或其他外部调度服务。
- 新增 Lark 表格字段或状态值。
- 自动处理错过目标日期的历史待发布记录。
